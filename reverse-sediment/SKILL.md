# Reverse Sediment（结论沉淀）

## 定位：这是审查器，不是总结器

对话记录本来就全在 transcript 里，随时能捞——**记录不稀缺，经过验证的判据才稀缺**。

凡是"写了等于没写"的总结长这样：

- 「我们尝试了 A，失败了，然后尝试 B」← 只有过程，没有判据
- 「需要注意 XX 问题」← 没说看到什么现象就该怀疑 XX
- 「结论：是 Y」← 没写怎么验证、有多确定、什么情况下会不成立

真正能复用的一条长这样：

> **微控制器双核时，改 HCPU 镜像不会改变 BLE 行为。**
> 判据：被分发的东西是 `0x9xxx` 段 = 跨核 IPC，不是应用协议。
> 复现：反汇编分发表，看 ID 空间落在哪一段。

前者下个会话要重新摸索，后者看一眼就能避开。

**所以本技能的产出不是文档，是"过筛子之后剩下的东西"。**

---

## 四个卡点（脚本会拦，不通过不让入库）

| 卡点 | 拦什么 | 为什么 |
|---|---|---|
| **① 置信度** | 必须三选一：`confirmed` / `suspected` / `refuted`。写"可能是"直接拒 | 模糊表述会在下游被当成确定事实引用 |
| **② 可复现** | 每条必须有 `verify`——一条能跑的命令或明确的观察步骤。写不出就降级或删掉 | **没有验证方法的结论 = 传闻**，几轮之后没人知道它当初怎么来的 |
| **③ 冲突** | 与现有 skill 里的旧结论做相似度召回，撞上了必须二选一 | 同一知识点散在两处、互相矛盾，比没有更糟 |
| **④ 已推翻记录** | `refuted` 必须写全 `was`（当初当成什么）+ `why_wrong`（为什么错） | 从同一个错误常量出发，下次一定推出同一个错结论 |

第 ④ 条是这个技能存在的主要理由。实战里被推翻的结论往往比正确结论更值钱：

```
错误常量（HERMES_MAGIC 写成样本自己的文件头）
  └─> 反推出假密钥 0xC6186C88
        └─> 推出"双区加密容器"
              └─> 据此设计了整套错误的解密流程
```

只记"正确答案是 X"不够，必须记"从哪一步开始错的"。否则换个人、换个会话，同一个坑再踩一遍。

## 工作流

### Step 0 · 先判断值不值得沉淀

只有满足**任意一条**才动手：

- 产生了新的**判据**（"看到 X 就判 Y"这种）
- 踩到了新的**坑**（尤其是"现象会误导你去修错误的地方"那种）
- 产出了新的**可执行工具**（脚本 / 命令 / 检验方法）
- **推翻了已有结论**

只是"又按已知流程跑了一遍"，直接告诉用户不用沉淀，别硬凑。

### Step 1 · 采集候选结论

从这次对话里挑句子，形态通常是：

- 「X 就是 Y」「X 在 A 不在 B」
- 「改 A 会 B」「A 之后必须立刻 B」
- 「看到 C 说明 D」
- 「之前以为 E，其实是 F」← **这条最容易被漏掉，必须收**

同时收集证据：日志片段、反汇编结果、抓包、实测现象、错误码。

### Step 2 · 逐条写 `verify`（最费劲也最关键的一步）

合格的 `verify` 长这样：

```
python scripts/sifli_bl_xref.py --image fw.bin --base 0x12070000 0x122917DC
```
```
给手表设一个 1 分钟后的计时器，手贴表盘能感到振动，且录音能看到 200Hz 附近的峰
```

不合格的：`"试一下"`、`"看日志"`、`"反汇编分析"` —— 换个人跑不出来就是没写。

**写不出 verify 时的处理顺序**：先降级成 `suspected` 并写清"还差哪一步验证" → 还是写不出 → 删掉，宁缺勿滥。

### Step 3 · 跑校验与冲突召回

```bash
python scripts/sediment.py template -o claims.json   # 拿空模板
# 填完 claims 之后
python scripts/sediment.py all claims.json -o out/
```

`all` = 校验 + 冲突召回 + 归属推断 + 渲染。校验不过就别往下走。

### Step 4 · 人工裁决冲突（脚本只负责召回，判定必须由人做）

相似度召回会给出"这条新结论跟旧文档第 N 行很像"。逐条判：

- **旧的是对的，新的是补充** → 合并成一条，别让同一知识点散两处
- **新证据更强，旧的错了** → 把旧的改成 `refuted`，写清 `why_wrong`，原位置**保留**并标注已推翻
- **两者说的是不同层面** → 分别保留，但各自加限定条件（"在 XX 前提下"），避免被当成矛盾

**不要默认"新的就是对的"。** 反过来也一样：新结论也可能是从错前提推出来的。

### Step 5 · 合并进目标 skill（不是新建碎片文件）

`render` 产出的是片段。**片段要被插进目标 skill 已有文档的对应章节**，
而不是在 skill 根目录堆一堆 `xxx.sediment.md`——那样等于没归档。

插入位置的选择：

| 结论性质 | 插到哪 |
|---|---|
| 判据、方法论 | `references/methodology.md` 或对象文档的"判据"章节 |
| 坑 | `references/pitfalls.md` 的对应分类下 |
| 某对象专有 | `references/<对象>.md` 的对应小节 |
| 已推翻 | 同类结论附近，**原位标注**，不要删掉原文 |
| 可执行 | `scripts/` 下新脚本，并在 `SKILL.md` 命令速查里加一行 |

插完更新 `SKILL.md` 的文档索引和 `README.md`（如果有）。

### Step 6 · 同步（用户确认后再做）

**产出后先把改动给用户看，确认了才 commit / push。** 不要自动推仓库。

```bash
git -C <repo> diff --stat      # 先给用户看改了什么
# 用户确认后
git -C <repo> add -A && git -C <repo> commit -m "..." && git -C <repo> push
```

如果 skill 同时存在于本机目录和仓库，两边都要同步，且**先在仓库改再拷回本机**（仓库是权威副本）。

## 命令速查

```bash
S=~/.workbuddy/skills/reverse-sediment/scripts/sediment.py

python $S template -o claims.json      # 空模板（含一条 refuted 示例）
python $S check    claims.json         # 只校验
python $S conflict claims.json         # 只做冲突召回
python $S route    claims.json         # 只推断归属
python $S render   claims.json -o out/ # 只渲染
python $S all      claims.json -o out/ # 一条龙
python $S index                        # 全部 skill 总览表（汇源用）
```

`index` 是"把多个项目汇到一起"的入口：先看现有 skill 有几斤几两，再决定新结论该并进哪个，
避免重复建技能。

## 写作硬规矩

详细规则见 `references/writing_rules.md`，骨架见 `references/skill_template.md`。

五条不能破：

1. **结论句要能独立成立**，不依赖上下文。把"它"换成具体名字。
2. **证据要具体到能复核**：地址、字节、时间戳、返回码，不要写"实测有效"。
3. **坑要写"误导性现象"**。只写"XX 不能用"没用，要写"XX 看起来像 YY，其实是 ZZ"。
4. **每个 references 文档至少对应一个可执行入口**。纯叙述的东西降级成笔记。
5. **不写"我们试了很多次"**。多少轮不重要，最后一轮为什么成立才重要。

**本技能不产生技术结论，只负责审查、去重、归位、成文。**
如果发现新结论无处可归（现有 skill 都不覆盖），才考虑新建 skill——
新建前先确认不是"没找到"，而是"真的没有"。
