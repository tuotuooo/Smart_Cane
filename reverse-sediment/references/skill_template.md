# references 文档骨架

> 复制这份骨架改，不要从空白页开始写。
> 结构顺序是有讲究的：**先给能直接用的结论，再给推导过程**。
> 读者 80% 的情况是"遇到问题来查判据"，不是"来读故事"。

## 写作要点

### 长度控制

| 内容 | 建议篇幅 |
|---|---|
| "先记住这几句" | 3~5 条，不超过 15 行 |
| 机制/架构 | 表格为主，散文不超过 3 段 |
| 判据表 | 现象多就多写，这是最有价值的一节 |
| 坑 | 一个坑 10~20 行，超过 30 行考虑拆独立文档 |
| 未闭合 | 有几条写几条，宁可空着也别硬凑 |

**单篇超过 800 行就拆**，按"对象"或"阶段"拆，不要按时间线拆。

### 必备 vs 可选

必备：一到三、四、五、六。
某节确实没有内容时，**留标题写"暂无"**，不要删掉——
删了会让读者以为"这块已经查清了"。

### 交叉引用

- 指向别的文档时写 `references/xxx.md §N`，带章节号
- 指向外部仓库时写全 URL
- 不要复制粘贴别处的段落，链接过去。**同一知识点只能有一个权威出处**

### 图 vs 表 vs 代码块

| 用什么 | 什么时候 |
|---|---|
| 表格 | 三个以上对象的属性对比、参数表、错误码 |
| 代码块 | 命令、字节序列、汇编、配置 |
| ASCII 流程图 | 状态机、数据流、时序（用 ``` 包起来） |
| 图片 | 基本不用。不能 grep、不能 diff、改不了 |

### 中英文混排

- 专有名词保留原文：`GATT`、`notify`、`HardFault`、`rt_device_control`
- 地址、寄存器、字节一律用**代码格式**
- 不要翻译 API 名字（"设备控制"→ 写成 `rt_device_control`）
