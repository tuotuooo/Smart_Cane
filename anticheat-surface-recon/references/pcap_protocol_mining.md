# 流量侧：pcap 解析与结构挖掘

> 原则：**先证明"能看到什么"，再谈"看到的是什么"。**
> 大部分关于游戏流量的错误结论，不是挖错了，是在挖之前没做口径自检。

---

## 一、读文件：pcapng 不能漏

Android 侧抓包工具（PCAPdroid、Wireshark）默认可能导出 **pcapng**，不是经典 pcap。
只认经典 pcap 会直接跑不动，报一个语焉不详的"格式错误"。

`pcap_analyze.py` 的 `read_pcapng()` 处理四种块：

| 块 | 作用 | 要注意的 |
|---|---|---|
| SHB（`0x0A0D0D0A`） | 段头，**字节序在此确定** | 看 BOM `4d 3c 2b 1a` |
| IDB | 接口描述 | 每个接口有自己的 `linktype` 和 `if_tsresol` |
| EPB | 增强包（带时间戳） | 按 `interface_id` 取对应 linktype |
| SPB | 简单包（无时间戳） | 时间戳要自己补，不能当 0 用 |

`if_tsresol` 决定时间戳精度（默认 1e-6，但也常见 1e-9），忽略它会让间隔分析整体偏 1000 倍。

## 二、剥二层：linktype 表

```python
LINKTYPE_RAW      = 101    # 裸 IP
LINKTYPE_NULL     = 0      # BSD loopback
LINKTYPE_ETHERNET = 1
LINKTYPE_LINUX_SLL  = 113  # 老 SLL，16 字节头
LINKTYPE_LINUX_SLL2 = 276  # 新 SLL2，20 字节头
LINKTYPE_IPV4     = 228
LINKTYPE_IPV6     = 229
LINKTYPE_NFLOG    = 239
```

`strip_l2` 必须按 `linktype` 分派，**不能按"前 N 字节像不像以太网头"猜**。
SLL 和 SLL2 的头长度不同（16 vs 20），猜错会让所有后续偏移整体位移。

## 三、UDP 流的四个客观问题

`udp_flow.py` 只回答可测量的事实，不猜语义：

| 问题 | 判据 | 典型读数 |
|---|---|---|
| 有几条流、5 元组是什么 | 按 `<src,sport,dst,dport>` 聚合 | 一条长连接 + 若干短连接 |
| **tick rate** | 下行包间隔的众数/中位数 | 33.3ms→30Hz、16.7ms→60Hz、50ms→20Hz |
| **载荷长度分布** | `len` 直方图 | 贴近 MTU = 分片快照；固定小包 = 心跳 |
| 是否加密 / KCP / QUIC | 首字节 + 魔数 + 熵 | UDP 443 首字节 `0xC0+` = QUIC 长头 |

**tick rate 是最有信息量的一个数**：它决定"服务端每秒推几次状态"，也就决定了
任何基于流量重建画面的方案的天花板。

## 四、结构挖掘三步（`snapshot_miner.py`）

目标：在没有符号、没有文档的前提下，判断下行快照里是否存在
「头部 + N × 固定 stride 的记录数组」。

| 步 | 做法 | 输出 |
|---|---|---|
| ① 列方差剖面 | 对每个字节偏移算跨快照方差 → `var[i]` | 哪些偏移是"变动的" |
| ② 剖面自相关 | 若存在 stride=s 的记录数组，则 `var[i] ≈ var[i+s]` → 在 s 的倍数上出现峰 | **候选 stride** |
| ③ 浮点列筛选 | 每偏移按 `<f` 解 float32，统计 `in_range`（|v|<1e6，排除 NaN/Inf/次正规）与 `smooth`（相邻快照 |Δ| 小） | **位置类字段候选** |

三条都是统计证据，**不下语义结论**。脚本说"这里可能有 stride=72 的记录数组"，
至于第 33 字节是什么，必须靠外部对照实验。

**两条读输出时必须做的复核：**

- **先看它挑的是哪条流。** 脚本按"结构强度"挑，**可能挑中上行而不是下行**。
  上行是你自己的遥测（移动/动作），下行才是服务端下发——两者语义完全不同，
  别把上行结论写成"服务端下发了什么"。
- **stride 接近最小包长时先怀疑碎片。** 同一会话里混着几十字节的心跳/ACK，
  会在自相关里造出一个跟包长同阶的假峰（实测见过 stride=29 被判显著）。
  复核方法：把长度直方图打出来，看那个 stride 是否对应一个独立的小包簇。

## 五、语义必须靠外部对照，不能靠看画面

本项目唯一被三重互证过的字段，做法是**把动作做成阶梯、每一步打毫秒时间戳、同时录屏**，
再用一个客观量给动作贴标签：

```
注入 motionevent DOWN/MOVE/UP（每步间隔已知）
  → 设备侧 date +%s.%N 打标记
  → screenrecord 同步录
  → 读 HUD 按钮区域亮度：蹲键 108.6→149.4、趴键 62.5→143.2（起身后回落）
```

亮度是客观量，能证明"这个按钮真的被按下去了、状态真的切了"；
这一步不做，就只能靠眼睛看画面猜"我刚才是不是蹲下了"，而猜错一次，
整张字段表的含义就全反了。

**两条由此得来的硬规矩：**

1. **包长分状态，统计前必须分组。** 实测：移动时出现 72B 包，静止时是 61B 主包 + 18B 心跳。
   把两种状态混在一起做直方图，得到的"分布"是假的。
2. **方向这类字段可能是世界坐标系，不是相对方向。** 同一会话里换个朝向，同样的前进动作
   编码完全不同。所以"8 个方向码"只能在**同一朝向下**当对照表用，跨会话直接失效。

## 六、失败模式（都会造出"看起来很漂亮"的假结论）

| 现象 | 根因 | 处置 |
|---|---|---|
| 长度分布全体落在同一个值（如全 29B） | **筛流口径 ≠ 统计口径**（筛的时候算了 UDP 头，统计时按 payload 算） | 先打印"payload 长度分布自检"，确认分母对 |
| 熵 ≥7.5 就判"加密了没救" | 熵高也可能只是压缩或高熵明文（字节码、浮点数组） | 先剥封装头再判；同时看列方差是否仍有结构 |
| 认不出封装层 | 反作弊会把游戏包再包一层 | 见下节定界规则 |
| 宿主侧全量抓包"零条游戏流量" | 流量走了别的接口 / App 内隔离抓包 | 用 App 级隔离抓包，不要用宿主全量 |

### 封装层定界（ACE 一类的做法）

```c
struct ace_udp_packet {   // 16 字节头
    u8  encrypt_type;  u8  algo_sel;  u16 reserved;
    u32 data_len;      u32 crc_header; u32 flags;
    u8  payload[];     // 尾部再跟 CRC32(4B)
};                         // UDP 载荷长 ≈ 16 + data_len + 4
```

**定界规则：`payload_len - 20 == data_len` 即视为封装包**，剥 20 字节再进 miner。
认不出就说明头结构不同——**这时候要判"未知"，不要判"加密"**。

> 关键事实：这类 SDK 通常**不持有自己的 socket**，靠游戏回调发出。
> 所以网关侧抓包一定能看到它，不会因为"它是独立通道"而漏掉。

## 七、口径自检清单（跑任何统计前先过一遍）

1. 分母是什么？包数 / 流数 / payload 字节数——**三者不能混**。
2. 时间戳精度对不对？（`if_tsresol`）
3. 有没有按状态分组？（移动 / 静止 / 开火 / 结算，包长和频率都不同）
4. 有没有把封装层剥掉？
5. 结论是"结构性自洽"还是"看起来很乱"？后者不算证据。
