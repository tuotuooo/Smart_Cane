# SiFli 振动/马达链路：双核架构、IPC 分发表与固件注入

> 目标场景：不碰 App，让手表按需振动（例如"任务完成提醒"）。
> 本文记录 2026-11-06 ~ 11-07 在 ASUS GTX20（SiFli SF32LB）上的完整分析结论，
> 包含**一个可以直接复用的注入方案**、**三个把刷机拖死一整天的客户端坑**，
> 以及**一次把表刷到不开机的事故复盘**。
> 通用固件手术手法见 `sifli_firmware_surgery.md`，OTA 传输见 `sifli_ota.md`。

---

## 一、先记住三句话

1. **振动有两套 API，一套安全一套会死锁。**
   `app_motor_control(mode)` 直接操作 RT-Thread 设备，任何上下文都能调；
   `vib_start(mode, cycles)` 走 `rt_mq_send` 消息队列，在消息分发器里调会**卡死**。
2. **BLE 收帧和马达驱动不在同一个核。**
   BLE 协议栈在 LCPU(Cortex-M33)，应用+UI+马达在 HCPU(Cortex-M55)。
   你改 HCPU 镜像里的"分发器"，**BLE 行为一点都不会变**——因为它根本不是 BLE 分发器。
3. **BLE → 振动的通路是现成的，只是被用例掩码挡住。**
   见 §四 `0x9009` 表项。理论上不需要刷机就能触发，但实测里面调的
   `vib_start(1,5)` 不振，原因未闭合（见 §六）。

## 二、双核架构（这是所有误判的根源）

| 核 | 型号 | 跑什么 |
|---|---|---|
| **LCPU** | Cortex-M33 | BLE 协议栈、`sifli_sd` GATT 服务、33 帧收发与分发、DFU 状态机 |
| **HCPU** | Cortex-M55 | LVGL 界面、应用逻辑（计算器/表盘/设置）、马达/背光等外设驱动 |

**怎么确认的：**

- 固件镜像里出现 46 处 `0x9xxx` 段的消息 ID —— 这是 SiFli 跨核 IPC 的消息号空间，
  不是应用层常量。
- `0x120E32E8` 的分发器只认这套 `0x9xxx` ID，线性比对、上界 0x110，
  典型的**核间消息路由表**形态。
- 把 `0x120E32E8` 换成 `b .`（自杀指令）刷进去，**BLE 侧完全无感**：
  命令照收、应答照回。当时误判成"表不是分发器，结论作废"，
  真实原因是**改对了位置但改错了核**。

> ⚠️ 教训：固件里找到一个"看起来像分发器"的东西，先确认它处理的是不是你要的那层协议。
> 判据是**被分发的东西的 ID 空间**，不是它长得像不像 switch。

## 三、马达 API 三兄弟

| 地址 | 符号 | 内部机制 | 在分发器里能调吗 |
|---|---|---|---|
| `0x120B3C98` | `app_motor_control(mode)` | `rt_device_control(dev, 0x23, &mode)` | ✅ 安全，无队列 |
| `0x121A1718` | `vib_start(mode, cycles)` | `rt_mq_send` IPC `0x8011` | ❌ **死锁** |
| `0x120C88C8` | `app_start_motor` | 未细查 | 未知 |
| `0x121A57A4` | `app_stop_motor` | 未细查 | 未知 |

`app_motor_control` 的 `mode`：`1` = 启动，`0` = 停止。
它是**唯一适合在中断/分发上下文里调用**的入口——没有内存分配、没有队列等待。

### 3.1 `vib_start` 的五个调用点

用 `sifli_bl_xref.py --base 0x12070000 0x121A1718` 扫出来的全部 BL/B.W 调用点：

```
0x12214694
0x122368F4
0x12236902
0x12246B32   ← find_device 处理器里面（0x900A）
0x1224769C   ← BLE 消息通知处理器尾部（0x9009）
```

`vib_start` 在这套固件里被用得很少，说明**大部分振动其实来自 App 层直接调
`app_motor_control`**，`vib_start` 只是给"提醒类"事件用的。

## 四、IPC 消息分发表（已完整解码）

```
基址   0x122917DC
布局   34 项 × 8 字节 = { u16 msg_id; u16 flag; u32 handler; }
分发器 0x120E32E8
        ldrh r2,[r0,#2]        @ 取 msg_id
        ... 线性比对，上界 0x110
        命中后尾调用 wrapper 0x12246A74  (blx r6)
```

两个关键表项：

| msg_id | handler | 干什么 | 里面有什么 |
|---|---|---|---|
| `0x9009` | `0x12247578` | BLE 消息到达通知 | 尾部 `vib_start(1,5)`；前面有 type 掩码 `0x00060100`，屏蔽 bit8/17/18 |
| `0x900A` | `0x12246AE4` | find_device（找表） | `vib_start(1,1)` |

**这就是 BLE→振动 的现成通路。** `0x9009` 的掩码说明：
不是每条 BLE 消息都振，只有 type 不落在 `0x00060100` 那三位上的才振。
换句话说，**发一条 type 干净的 BLE 消息，理论上设备自己就会振一下**——
不需要刷任何固件。

代价是：这条路依赖 LCPU 侧的 type 判定逻辑，而我们没有 LCPU 镜像，
无法验证哪些 type 会被放行。实测里反复试过的命令没有一条触发，
所以最终转向了 HCPU 侧注入（§五）。

## 五、注入方案（可用，但尚未在设备上验证成功）

### 5.1 挂载点选择

| 项 | 值 | 说明 |
|---|---|---|
| 挂载地址 | `0x120E32E8` | 原指令 `10 b5 42 88` = `push {r4,lr}` + `ldrh r2,[r0,#2]`，正好 4 字节 |
| 补丁内容 | `b.w 0x12070670` | 3 个 16 位字的 Thumb-2 长跳转 |
| 代码洞 | `0x12070670`，约 144 B 全零 | 紧邻内置计算器的尾部（计算器占 `0x120701D0`~`0x1207066F`） |
| 恢复点 | `0x120E32EC` | 分发器第 3 条指令 |

### 5.2 钩子必须做的事

1. 保存现场（**保持 8 字节栈对齐**，否则浮点/NEON 上下文会炸）
2. 调 `app_motor_control(1)`
3. 忙等一段时间（不要调 `rt_thread_mdelay`，分发器上下文里可能不可用）
4. 调 `app_motor_control(0)`
5. **原样执行被覆盖的那两条指令**（`push {r4,lr}` / `ldrh r2,[r0,#2]`）
6. 跳回 `0x120E32EC`

漏掉第 5 步是最常见的死法：堆栈少压一次 `r4`，返回时 `pc` 取错，直接 HardFault。

### 5.3 用汇编器，不要手写机器码

本机有 **ARM GNU Toolchain**：
`C:\Program Files (x86)\Arm GNU Toolchain arm-none-eabi\14.2 rel1\bin\`

```bash
B=".../bin"
"$B/arm-none-eabi-as" -mcpu=cortex-m33 -mthumb kit/motor_hook.s -o hook.o
"$B/arm-none-eabi-ld" -T kit/motor_hook.ld hook.o -o hook.elf      # ← 这一步不能省
"$B/arm-none-eabi-objcopy" -O binary -j .text hook.elf hook.bin

"$B/arm-none-eabi-as" -mcpu=cortex-m33 -mthumb kit/jmp.s -o jmp.o
"$B/arm-none-eabi-ld" -Ttext=0x120E32E8 jmp.o -o jmp.elf
"$B/arm-none-eabi-objcopy" -O binary -j .text jmp.elf jmp.bin
```

产物：`hook.bin` = 40 B，`jmp.bin` = 4 B。用 `sifli_fw_patch.py` 分别写进
`0x12070670` 和 `0x120E32E8`。

**两个必须注意的点：**

1. **`-mcpu=cortex-m55` 在 14.2.Rel1 上不被识别**（实测报 `unknown cpu`）。
   用 `-mcpu=cortex-m33`（同为 ARMv8-M，本钩子用到的指令集完全够）或
   `-march=armv8.1-m.main`。
2. **必须走链接器，不然 BL 偏移全错。** `BL`/`B.W` 的编码是**相对 PC 的偏移**；
   直接 `as` + `objcopy` 得到的二进制是按基址 0 算的偏移，
   烧到 `0x12070670` 上就会跳进垃圾地址 —— 表现为开机即死。
   验证方法：链接后 `objdump -d` 应显示
   `12070674: bl 120b3c98`（目标地址正确），而不是 `bl 000b3c98`。

手写机器码的问题不是"难"，而是**偏移和字面量池位置一旦算错，
错误会静默传播到设备上，表现为随机死机**。

### 5.4 打包与刷写

```bash
# 签名打包（fw_ver 只能是 1001001）
python scripts/sifli_fw_pack.py --keys <sifli02> --image fw_motor.bin \
       --fw-ver 1001001 -o pkg_motor

# 一键刷写（父进程进 DFU，子进程推流）
python scripts/sifli_ota_flash.py --ctrl pkg_motor.ctrl --blocks pkg_motor.blocks
```

## 六、为什么 `vib_start(1,5)` 不振（未闭合）

实测：在健康固件上通过其他手段调到 `vib_start(1,5)`，**没有任何振动**。
可能原因（按可能性排序）：

1. **`cycles` 不是"次数"** —— 可能是"持续 tick 数"，5 太小，马达还没来得及起转就停了
2. **马达驱动器需要先使能** —— 也许要先 `app_motor_control` 或写某个 GPIO/PMIC 寄存器
3. **`0x8011` 消息在目标核上没有静态 handler** —— 我们扫了 HCPU 镜像，`0x8011`
   在分发表里查不到（表里只有 `0x9xxx` 段），说明它归 LCPU 或另一个线程管，
   发出去就石沉大海

**结论：注入钩子里不要用 `vib_start`，用 `app_motor_control` 并在外面用忙等控时长。**

## 七、事故复盘：从 DFU 0% 到"不开机"

### 7.1 发生链

```
推送 → 进 GTX20 成功 → 发 START(0x06) → 等应答 → 0 条通知 → 卡 0% 19.5s 超时
     → 用户长按强制重启 → 屏幕黑 → 长按电源无反应 → BLE 扫不到、按 MAC 连不上
```

### 7.2 三个客户端坑（都不是设备的问题）

**坑一：同进程二次连接，GATT 拿不全**

父进程刚断开一次 GATT，紧接着在同一事件循环里再连、再 read START 应答 →
**收到 0 条 notify**，看起来像设备不响应。
改成"父进程只负责把设备送进 DFU，推流交给独立子进程"才对。

判据：如果 START 发出去了但一条通知都没回来，先怀疑本地连接状态，不要怀疑设备。

**坑二：`fw_ver` 大了会被静默拒**

`1001002` → `ctrl` 应答就是拒绝；`1001001`（与历史成功过的包一致）→ 顺利进 DFU。
设备端的版本比较是 `>=` 还是 `>` 没确认，**保守做法：永远用和上次成功一致的号**。

**坑三：GTX20 模式不广播**

DFU 模式的设备**不发广播包**，BLE 扫描列表里永远是空的。
只能靠 `BleakClient("2F:A2:CD:E2:B5:F1")` 按地址直连，而这依赖 **Windows 蓝牙地址缓存**。
缓存过期 → `BleakDeviceNotFoundError` → 死活连不上 → 卡 0%。

这条是那次事故的直接触发点，也是最容易误判成"设备变砖"的假象。
**下次进 DFU 后立刻推流，不要中间插入任何需要重连的步骤。**

### 7.3 为什么可能真的擦空了

DFU 的 `START(0x06)` 在部分 bootloader 上会**先擦除目标分区再等数据**。
如果擦了但 0 字节写入，应用区就是空的 → 重启后 bootloader 找不到有效镜像
→ 可能停在 DFU（不广播）或直接黑屏。

这与"电池耗尽"的表现**几乎完全一致**，只能靠硬件现象区分：

| 现象 | 判读 |
|---|---|
| 插充电器 5~10 分钟内出现充电图标/背光 | 电池活着，虚惊一场 |
| 30 分钟后长按 15 秒能亮 | 应用区被擦，但 bootloader 完好 → 重刷即可 |
| 60 分钟完全无反应、无背光、无振动 | 只能走硬件烧录（§八） |

### 7.4 电池耗尽的证据链

出事时的三次检测（结果一致）：

- 主动扫描 25 秒，周围 20 台 BLE 设备全部枚举出来了，**手表零信号**
- 按 MAC 直连 → `DeviceNotFound`
- 查 Windows 蓝牙栈 → 只剩经典音频（GTX20 Hands-Free）的历史配对残留，BLE 侧全无

加上"长按电源也不亮"，**首选判断是电池耗尽**：
DFU 那个箭头界面屏幕常亮，功耗最大，而我们已经在里面耗了 20 多分钟。

## 八、救砖路径

按代价从低到高：

1. **充电 60 分钟**（先排除电量）
2. **长按电源 15~20 秒** 强制断电再上电
3. **进 DFU 重刷原厂镜像**：如果 bootloader 还活着，`sifli_ota_flash.py` 直接能刷
4. **硬件烧录**：`sftool.exe`（`sifli_sdk/tools/`）+ UART4 + bootmode 跳线
   - **SWD 优于 UART**（不需要跳线时序，直接 halt 内核）
   - 这颗芯片 **secboot 无失败计数、无回滚**，只要 CPU 能起来就一定能救

---

## 九、下次动固件之前

按这个顺序做，别再跳：

1. **备份原厂镜像**，并确认备份能原样刷回去（先刷一次原厂，验证链路）
2. **最小改动验证**：先只改一个字符串常量（版本号），确认"改了 → 刷了 → 生效了"
3. **确认电量**：`>= 50%`，或者插着充电器刷
4. **一次性完成**：进 DFU 之后连续推完，中间不重连、不探测、不打印多余日志
5. **注入前先想清楚"这行代码跑得到吗"** —— 六轮语言包失败换来的教训，
   同样适用于马达：`vib_start` 那条路跑不到，就不要在那儿加钩子
