# 数据面还原：从空口日志还原"文件传输协议 + 容器格式"

> 对象：**物理设备**。前置是 `methodology.md` 附录 A（怎么开 HCI 日志、怎么取回）。
> 这里解决的是拿到日志之后的下一步：**一个字节都没见过的私有协议，怎么在几小时内拆开。**

---

## 一、什么时候走这条路

| 处境 | 该走的路 |
|------|---------|
| 有 PC 蓝牙适配器，能自己连设备 | 直接 `recon.py probe`，主动发帧试 —— 快 |
| 设备已经和手机 App 绑定，且绑定态有云同步/风控 | **空口抓包** —— 不打断绑定，拿的是真流量 |
| App 里没有"导入/发送"入口，或入口依赖实连 | **空口抓包** —— 绕过 UI，直接看它发了什么 |
| 只想确认"这条通道能不能写" | `recon.py probe` 足够，不用抓包 |

空口抓包的最大优势：**你拿到的是厂商自己实现的完整正确流程**，不用猜握手、不用猜重试。
最大劣势：**没有协议文档，只能从字节反推**。

---

## 二、三步法

```
① 定位流：哪个 handle、哪个方向、多少字节
② 定界  ：控制帧 vs 数据帧，帧头几个字节
③ 立信  ：用它自己的校验和/长度字段自证「我拆对了」
```

第 ③ 步是这个方法能不能收敛的关键。**没有自证环节，你永远不知道自己拆得对不对。**

---

## 三、定位流：先做统计，别急着看 hex

```bash
python <skill>/scripts/snoop_parse.py info hci.bin
```

输出会给出：

- **包类型分布**：正常应该是 ACL 占绝大多数。若出现"几百 KB 的 CMD、零个 ACL"，
  说明 H4 类型判错了（见附录 A 细节 1），先修解析器再看。
- **ATT 操作码分布**：`WRITE_CMD(0x52)` / `WRITE_REQ(0x12)` / `NOTIFY(0x1b)` 各多少。
- **按 handle 的流量榜**：谁在传数据一目了然。

判据：

| 特征 | 结论 |
|------|------|
| 某个 handle 上有上千个 `WRITE_CMD`、每包接近 MTU | **文件传输**，就是它 |
| 有来有回的 `WRITE_REQ` + `WRITE_RSP`，载荷 5~20B | 命令通道 |
| `NOTIFY` 周期性出现、长度固定 | 传感器上报 |
| 同一个 handle 三种都有 | 透传特征值，语义在应用层，不在 ATT 层 |

**别把"命令通道"当数据通道去拆。** 同一个设备常常两个都有，
文件走的那个通常包最大、数量最多。

---

## 四、定界：怎么找出帧头

拿到载荷流之后，**不要从头硬读**。做两件事：

### 4.1 看首字节的频率分布

```python
collections.Counter(f[0] for f in frames).most_common(10)
```

命令字节一定是**低频**的（只有几种），数据字节是均匀分布的。
低频的那几个值就是候选帧头。悦心S1 上 `0xd1` 出现 1800+ 次、其它首字节几乎不重复。

### 4.2 找"小而固定"的帧

数据帧大（200+ B）、控制帧小（4~20 B）。把长度排序，两头分别看 hex：

```
小帧：d1 05 0a                    ← 会话开始
      d1 03 f3 82 00 00           ← 结束 + 校验
大帧：d1 02 00 <252 字节>          ← 数据块
```

**控制帧的形态会直接把协议结构告诉你**：第三字节是 key，后面是参数。

### 4.3 一个反直觉的判据：数据帧里有没有序号

如果数据帧是 `cmd + 固定 1 字节 + 纯数据`，**没有序号也没有偏移**，
那它是**纯流式追加**：设备按到达顺序写文件，丢一包就整包废。

这决定了两件事：
- 传输必须可靠（BLE 的 Write Command 无确认，所以厂商会在最后加整包校验）
- **你重放时也只能顺序发**，不能跳着补

## 五、立信：校验和怎么试

按这个顺序试，命中率从高到低：

| 顺序 | 算法 | 说明 |
|------|------|------|
| 1 | **字节累加和 & 0xFFFF** | 最常被忽略，但嵌入式最爱用。悦心S1 就是它 |
| 2 | CRC16 的 `CCITT-FALSE / XMODEM / MODBUS / ARC` | 四种变体覆盖大多数 |
| 3 | CRC32 | 一般只在大文件/固件上用 |
| 4 | MD5/SHA1 前 N 字节 | 有 crypto 库的方案 |

**验证方法**：拿两个不同文件各自的"结束帧"和实际数据算，两个都对上才算确认。
一个对上可能是巧合（尤其小文件）。

悦心S1 实测：`contacts.ml` 361B → `0x82F3`，`wf_w202.watch` 433835B → `0x02AE`，
两次都是纯累加和，一次命中。CRC16 七种变体全部不匹配。

> **诚实标注**：结束帧还有 2 字节没解（`contacts=0`、`表盘=0x0365=869`）。
> 已排除"CRC16 / 长度 / 块数"，但没确认是什么。**写进文档时标"未解"，不要编。**

## 六、容器还原：靠"偏移连续"自证

文件传完了，里面还是个私有容器。通用拆法：

```
[magic:4] [header_size:2] [version:2] [count:2] [其它头字段] [names_len:4]
[名字表：全路径，\0 分隔]
[索引表：count × 每条固定长度]
[数据区]
```

**验证技巧（最重要的一条）**：索引表里的 `data_offset` 应该**严格连续**：

```
[0] off=    32 size=    72   → 下一个 104
[1] off=   104 size= 17572   → 下一个 17676
[2] off= 17676 size=  2476   → 下一个 20152
```

`off[i] + size[i] == off[i+1]` 全部成立 → 你解对了。
只要有一个洞，要么字段读错了，要么中间有对齐填充。

**这次就靠这条推翻了"8KB 对齐"的旧结论**：
总长 `32 + 8335 + 1936 + 423532 = 433835`，与文件大小**精确相等**，一个填充字节都没有。
旧结论来自 DWARF 里的 `mkSifliDialFile`（本地制作工具），云端下发走的是另一条打包路径。
**同一个格式，两种打包器，别把工具的行为当成格式的规范。**

> 小坑：`data_offset` 可能带一个固定偏移（本例是 `+32`）。
> 判据是"第 0 个文件的 offset 减掉这个常量后，正好等于它在文件里的实际位置"。

## 七、判"这是资源还是程序"

这决定你后面能做什么，判错会白干几天。

| 证据 | 结论 |
|------|------|
| 内含条目里有 `ELF` 魔数（`7f 45 4c 46`） | **是程序**，逻辑在 so 里 |
| so 的导入符号是 `lv_img_set_src` / `lv_obj_align` / `lv_task_del` | LVGL 动态模块（dlmodule） |
| 导入符号是 `dlmodule_get_user_data` / `service_get_current_time` | 跑在 RTOS 上，有宿主 API |
| 只有图片 + 一个描述文本 | 纯资源包，换图即可 |
| 有个 `.dsc` 小文件，内容是 `<kind:u8><len:u8><name>\0` 重复 | 模块清单，声明入口与资源 |

**"表盘不是图片，是程序"** 这个判断，直接决定了工作量差一个数量级：
换图是几小时，改逻辑要 SDK + 交叉编译。

## 八、复现（要自己发的时候）

抓到的流量已经告诉你全部参数，照抄即可：

| 参数 | 从哪读 |
|------|--------|
| 特征值 handle | `snoop_parse info` 的流量榜 |
| MTU | `ATT_MTU_REQ/RSP` 帧 |
| 写方式 | `0x52`=无响应（快，但丢包不可知）/ `0x12`=有响应 |
| 单包载荷 | 数据帧的最大长度（不是 MTU，厂商常留几字节头） |
| 帧间隔 | 时间戳差值；密集发送可能触发设备端缓冲溢出 |

**发送端最容易翻车的地方是"发太快"**。厂商 App 有节流，你照抄时间戳节奏最安全。

## 九、这套方法的产出，以及它的边界

产出（悦心S1 实测，一次抓包全部拿到）：

- 传输协议：`d1 05`(开始) / `d1 01`(文件名+大小) / `d1 02`(数据) / `d1 03`(校验)
- 容器格式：`head_t` + 名表 + 索引 + 数据区，433,835 字节精确闭合
- 一个真实表盘文件的**无损还原**

边界（必须写进报告）：

- **只还原了"App 发什么"，没验证"设备收不收别人的"**。设备可能校验来源、
  可能有会话密钥、可能只接受特定版本。要证这条，得自己发一次。
- **未解字段就是未解**。`d1 03` 后 2 字节、`d1 05 0a` 的确切语义、
  `head_t` 里 0x0A 的 4 字节 —— 全部标未解。
- **重放 ≠ 可用**。能重组出文件，不等于能把你改过的文件推回去。

## 十、一页速查

```
抓（附录 A）→ info（找流）→ 看首字节频率（找帧头）
→ 看小帧形态（定控制/数据）→ 试累加和（立信）
→ 拆容器（偏移连续自证）→ 判 ELF（资源 or 程序）→ 照抄参数复现
```

**每一步都要有自证**：包类型分布对不对、长度字段闭不闭合、校验和对不对得上。
没有自证的推断，一律标"推测"。
