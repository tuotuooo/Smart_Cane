# 坑：原生二进制 + 服务端授权逆向（实测，按代价排序）

> 每条格式固定：**现象 → 根因 → 判据（下次怎么一眼认出来）→ 复现**。
> 复现命令写不出来的结论不许进这份文档（见 `reverse-sediment` 的四卡点）。

---

## 坑 1：返回值语义被注释搞反 —— 整轮排查走偏

**现象**：`activate_number_validate_normal` 返回 1，团队以为是"失败"，于是开始找"为什么失败"，
浪费大量时间在错误方向上。
**根因**：早期逆向笔记把 `1 = 有效` 记成了 `0 = 有效`，后续所有推理都建立在这个错误常量上。
**判据**：任何"返回码语义"结论，必须用**已知有效样本 + 已知无效样本**各跑一次钉死。
**复现**：

```bash
python scripts/oracle_harness.py --lib lib.so --func validate --call "<已知有效码>"  # 记下值
python scripts/oracle_harness.py --lib lib.so --func validate --call "<明显无效码>"  # 对比
```

## 坑 2：`ret=0` 但系统没激活 —— 返回值不是判据

**现象**：函数返回 0，程序打印"激活成功"，但重启后仍是未激活。
**根因**：存在 **escape 旁路**——某条早期返回分支只写一个占位文件
（`/etc/.kyactivation.place`）然后直接 `return 0`，真正的激活文件（`/etc/.kyactivation`）没写。
**判据**：`ret=0` 之后立刻核对**落盘文件的内容**，而不是文件名存在与否。
**复现**：`cat /etc/.kyactivation; ls -la /etc/.kyactivation*; reboot` 后再看状态。

## 坑 3：`LD_PRELOAD` hook 残留导致 `ret=13`

**现象**：昨天还能成功的操作，今天同一命令返回 13（"保存失败"），代码和参数都没变。
**根因**：上一轮实验的 hook 还挂在环境里，把 `activation_code_save` 截断了——业务层以为
存成功（返回 True），实际没落盘，上层核对时判失败。
**判据**：任何 `ret=13`/`ret=保存类错误`，**先跑 `env | grep -i preload`**。
**复现**：`env | grep LD_PRELOAD` → 摘掉 → 同一命令再跑一次。

## 坑 4：进程内缓存 —— 改了 DB 不生效

**现象**：往数据库插了记录，接口仍返回旧数据 / 新记录不出现。
**根因**：守护进程启动时把序列号/list 读进内存缓存；另有单例对象
（`LicenseManager._instance`）跨调用持有旧状态。
**判据**：DB 改动后接口无变化 → 先 `docker restart <daemon>` 再判。
**复现**：`docker exec <c> grep -n "_instance\|def init_manager" /path/daemon.py`；
重启后重调接口对比。

## 坑 5：PIE / 编译差异 —— 本地反汇编的地址在目标机上不存在

**现象**：本地 `capstone` 反汇编 `.so` 得到的函数地址，拿到目标机 `gdb` 里对不上，
甚至本地可执行文件的段布局与目标机完全不同。
**根因**：PIE + 不同编译选项；`.so` 的 `.text` 段恰好 VA == 文件偏移，可执行文件往往不成立。
**判据**：**本地 RE 只用来理解逻辑，地址一律在目标机上用 `objdump`/`nm` 重新确认。**
**复现**：`ssh <target> 'objdump -d -M intel /usr/bin/target | grep -A20 "<addr>"'`

## 坑 6：日期编码多对一 —— 别用"换日期失效"证明日期参与校验

**现象**：把码里的日期段改掉，校验仍然通过；于是结论"日期不参与校验"看起来成立，
但另一组实验里改日期又确实失效了，结论反复。
**根因**：日期编码是**多对一**的（不同编码串解码出同一日期，如 `S9P3`/`S9P5` → 同一天）；
且日期段本身常常不在 `strncmp` 比对范围内。
**判据**：判断某段是否参与比对，**看比对式**（`strncmp` 的偏移/长度），不看"改了有没有效果"。
**复现**：`objdump -d` 搜 `strncmp`/`memcmp`/`cmp` 常量长度。

## 坑 7：本地没有 binutils —— 硬装不如在目标机跑

**现象**：Windows/精简环境没有 `objdump`/`nm`/`readelf`，于是试图本地编译一套，
或改用第三方反汇编库导出符号。
**根因**：符号表在**目标文件里**，最权威的读取环境就是目标机。
**判据**：符号相关的一切（`nm -D`、`objdump -T`）**一律 SSH 到目标机执行**；
本地只用 `capstone` 做纯字节反汇编（不依赖符号），且地址不采信（见坑 5）。
**复现**：`ssh <target> 'nm -D --defined-only /usr/lib/lib.so | head'`

## 坑 8：容器里 `grep -r /` 直接卡死被 kill

**现象**：`docker exec <c> grep -rl "keyword" /` 长时间无输出，最终命令被中断，没有任何结果。
**根因**：容器内虚拟文件系统（`/proc`、`/sys`、镜像层）体量巨大，全盘递归扫描会 OOM。
**判据**：**永远限定目录**：`/app`、`/usr/share/<pkg>`、`/opt`，或先 `find -maxdepth 6` 拿清单。
**复现**：`docker exec <c> sh -c "find /usr/share -maxdepth 6 -name '*.py' | head"` 再针对性 grep。

## 坑 9：文档里的占位名被当成系统真值

**现象**：为方便描述，文档里给某实体起了个"看起来像真的"的编号（如 `G19953`），
几轮之后它被当成系统里真实存在的值去查询，查不到 → 又去排查"为什么查不到"。
**根因**：占位别名与真实标识混用，且没有显式标注"这是占位"。
**判据**：**凡是文档里出现的编号，必须标注来源**：`实测值` / `派生值（可复现命令）` / `占位别名（非系统值）`。
**复现**：`grep -n "<编号>" references/*.md` 检查每处是否带来源标注。

## 坑 10：服务端零校验 ≠ 结构正确

**现象**：把 `G` 开头的字符串塞进本来是纯数字的 serial 字段，服务端照单全收、建库成功，
于是认为"这说明 G 开头才是正确用法"。
**根因**：服务端造号入口只接收参数并落库（`license_type` 硬编码），**不校验 serial 形态**；
"能写进去"只证明**没有格式校验**，不证明**符合设计**。
**判据**：区分「**没有校验**」与「**被接受为正确**」——前者是能力边界，后者才需要语义证据。
**复现**：读造号脚本入参（`grep -n "def main\|argparse\|license_type"`），确认它做了哪些校验。
