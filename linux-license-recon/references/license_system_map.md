# 授权系统对象地图：先啃哪一层、用什么做判据

> 适用：桌面/服务端的激活码、License 服务、离线授权。
> **不适用**：纯远程校验（那归 `web-js-reverse`）、硬件内授权（归 `ble-device-recon`）。
> 关联：`pitfalls.md`（坑）、`case_kms_kylin.md`（完整实证）

---

## 一、先记住这几句

1. **客户端是校验器，服务端是事实源。** 90% 的判定逻辑在服务端明文脚本 + DB 里，不在 ELF 里。
2. **不重写算法，调用真实函数。** 造码器只是真实校验函数的调用方，不是它的第二实现。
3. **码布局从比对点反推**（`strncmp` 的偏移/长度），不从编码算法反推。
4. **`ret=0` 不算成功，落盘内容才算。** 返回值有旁路、有被 hook 截断的、有注释写反的。
5. **本地推出来的地址，在目标机上必须重新确认**（PIE/编译差异）。

---

## 二、三层对象与优先级

| 层 | 对象 | 拿到什么 | 成本 |
|---|---|---|---|
| L1 | **服务端明文源码**（`.py` / `.sh` / 配置） | 关联字段、发码入口、校验函数名与行号、错误码含义 | 极低 |
| L2 | **字节码 / Cython / Boost.Python 扩展**（`.so`） | 函数签名（`dir`/`inspect`）、输入输出行为、内部常量 | 中 |
| L3 | **客户端 ELF 可执行文件** | 校验入口、算法常量、返回码分支、码布局比对点 | 高 |

**判据：先看 L1 存在吗。** K-KMS 实例：容器里 `/usr/share/xxx/daemon.py` 是明文 Python，
`grep -n "f_type\|activate_for\|def gen_key"` 十分钟拿到全部关键行号，而客户端反汇编花了两周。
**只有在 L1/L2 都拿不到时，才值得上 L3。**

**怎么找 L1：**

```bash
# 容器里是不是有明文脚本
docker ps --format "{{.Names}}"
docker exec <c> sh -c "find / -maxdepth 6 -name '*.py' 2>/dev/null | head"
# 进程 1 的真实命令行（判断是 Python 还是编译产物）
docker exec <c> cat /proc/1/cmdline | tr '\0' ' '
```

⚠️ **别在全文件系统上 `grep -r /`**——容器里会直接卡死被 OOM kill。
限定到 `/app`、`/usr/share/<pkg>`、`/opt` 这些目录，或先 `find -maxdepth` 拿清单。

## 三、oracle 化：把真实函数变成可反复调用的判据

**问题**：Cython 编译的 `.so` 没有源码，`inspect.getsource` 失效；靠输入输出猜算法，
猜出来的是"我认为的实现"，不是"真实的实现"。

**做法**：`ctypes` dlopen 真实 `.so`，把**真实校验函数**直接当 oracle 调。

```python
import ctypes
lib = ctypes.CDLL('/usr/lib/liblicense.so')
fn = lib.activate_number_validate_normal
fn.argtypes = [ctypes.c_char_p] * 4   # hw_id, serial, code, product_type
fn.restype = ctypes.c_int
print(fn(b'AA:BB:CC:DD:EE:FF', b'200017888', b'CODE...', b'02'))  # 1 = 有效
```

**三条纪律：**

1. **签名靠试探，不靠猜**：`dir(obj)` 列方法、`inspect.signature()` 拿参数量、
   `__code__.co_varnames` 拿参数名（纯 Python 部分有效）；`.so` 部分只能用
   `argtypes` 逐个试——错签名会段错误，**先用手工构造的最小参数在子进程里试**。
2. **判"有效"的返回值要实测确认**：K-KMS 的 `validate` 返回 **1 = 有效**（不是 0），
   早期注释搞反导致整轮排查走偏。用已知有效的码做正样本、已知无效的码做负样本，
   一次就能钉死语义。
3. **非确定性要显式检测**：同一组输入连跑 3 次，输出不同 → 内部有随机源
   （ECC nonce / 时间戳 / 随机字典偏移），此时**不能"生成一次就信"**，必须
   "生成 → 校验 → 失败重试"的循环。→ `scripts/oracle_harness.py --repeat 3`

## 四、码结构反推：找比对点，不找算法

授权码通常是固定布局的字符串，校验实现的骨架长这样：

```c
if (strncmp(code, gen_prefix, 14) != 0) return 9;      // 前 14 位匹配
if (strncmp(code + 18, gen_suffix, 2) != 0) return 9;  // 第 19-20 位匹配
```

**从这两行就能读出整条码的布局**：`[0:14] 主体` + `[14:18] 日期段` + `[18:20] 后缀`。
其中**日期段不参与比对**（只影响展示/有效期），所以"换日期码失效"这类结论多半是错的。

| 现象 | 判读 |
|---|---|
| 只比前 14 位 + 后 2 位 | 中间 4 位是元数据（日期/类型），可任意填 |
| 比对长度 = 码长 − 后缀 | 后缀是"版本/批次"标签，独立生成 |
| 返回码分布很细（7/9/13/72） | 每个 ret 对应一个分支，**ret 表就是函数地图** |
| 同一码多次校验结果不同 | 有随机源，见 §三 纪律 3 |

**反推步骤**：① 收集全部 ret 值与触发条件 → ② 找 `strncmp/memcmp` 的常量长度与偏移 →
③ 用"只改一位"的码做梯度测试确认哪段参与比对 → ④ 得到布局后，主体段用 oracle 暴力/字典法生成。

## 五、数据段字典表：算法的另一半在数据里

编码/混淆算法常常依赖一张**固定的字符表**，它躺在 `.rodata` 或 `.bss` 里：

```bash
objdump -h lib.so | grep -E "\.rodata|\.bss"     # 拿段地址与大小
objdump -s -j .rodata lib.so | head -40          # 看内容
# 已知偏移时直接读（脚本里 open().read() + seek 即可，无需反汇编）
```

K-KMS 实例：编码字典在 `.bss` 的固定偏移（`0x43f80`），导出后造码器直接 `dict_struct` 读取，
不必逆"字典怎么构造出来的"。**判据：如果算法里有 `table[i % n]` 这种形状，先找表。**

## 六、副作用判据：怎么确认"真的生效了"

| 判据 | 可信度 | 说明 |
|---|---|---|
| 程序打印"激活成功" | ❌ 最低 | 文案与状态机无关 |
| 函数返回值 | ⚠️ 中 | 有 escape 旁路、有注释反了的、有被 hook 截断的 |
| **落盘文件内容** | ✅ 高 | 激活码原文、有效期、hwid 写进哪里，一看便知 |
| **DB / 服务端状态** | ✅ 高 | 授权池结构、绑定关系、剩余次数 |
| **重启后仍然有效** | ✅ 最高 | 能过重启说明持久化真的完成了 |

**K-KMS 踩过的具体形态**：正常路径写 `/etc/.kyactivation`（含激活码原文）；
某条 escape 旁路只写 `/etc/.kyactivation.place` 然后直接 `return 0`——
两者返回码一样，**只有看文件名/内容才能区分**。

同理，`LD_PRELOAD` hook 截断了 `activation_code_save`（返回 True 但不落盘）时，
上层 save 判定失败 → 返回 13。排查时**先摘 hook 再跑**。

## 七、GPG / 证书闸门：先判它在不在关键路径上

授权系统里常有 GPG 签名校验、证书链、加密 LICENSE BLOCK，看起来是硬闸门。

**判据：绕开它还能不能达成目标？**

K-KMS 实例：GPG 校验在 worker 线程（`0x1b8ad`）里，**不在** CLI 激活链
（`0x227f7 → 0x200ef → … → ret=0`）上。也就是说"厂商私钥"根本不是必要条件，
整条链纯粹是离线算法驱动。**结论：闸门的存在 ≠ 闸门在路径上。**

方法：把入口到出口的调用链画出来（`objdump -d` + `nm` 找符号边界），
逐个确认闸门是否被这条链调用；不在链上的，直接忽略。

## 八、加密容器：能读到头部就是胜利

`FORMAT:2` 这类自定义容器常常是**明文头 + 加密体**：

- 明文头给出：serial、模式（永久/限期）、数量、有效期、产品类型
- 加密体（外部密钥/私钥解不开）：LICENSE BLOCK 主体

**判据**：头部字段足以确认"这确实是厂商 license、给了多少额度、是不是永久"，
不必解加密体。**先把头部解析出来，再决定要不要为加密体投入。**
